# Démo v2 — Outil interactif d'hébergement d'urgence (politique simulée, A350, temps réel)

Plan de développement d'origine du 11 septembre 2026, reproduit tel quel pour référence. Le cahier des charges (`../CAHIER_DES_CHARGES.md`) prévaut en cas de divergence.

## Context

Le POC v1 (31/08, `hai-admin-mcp/tools/rebooking.mjs`) a validé la chaîne « liste passagers
→ agents Holo → plan d'hébergement » en CLI sur un scénario NOU→CDG bloqué à Bangkok, avec
une liste **fixe** de 4 hôtels. Le client veut une **démo pilotable** : l'utilisateur
définit une politique d'hébergement et la configuration du vol dans une interface web,
lance le run, et regarde les agents travailler **en temps réel**.

Décisions utilisateur (11/09) : A350-900 tri-classe plein (34 J / 24 W / 266 Y,
éditable) · **découverte dynamique des hôtels par zone** (plus de liste fixe) · politique
par défaut complète **éditable dans le formulaire** · **appli web locale complète**
(serveur Node du dépôt, clé API côté serveur). Invariants : prix publics uniquement (pas
d'accords groupes), **aucune réservation** (arrêt à la page de sélection des chambres,
CAPTCHA signalé jamais contourné).

Contraintes vérifiées (exploration + 2 agents de conception, 11/09) :
- Dépôt inchangé depuis le 31/08 ; **pas de git**. `hono`/`express` seulement transitifs → ne pas s'y adosser.
- SDK `hai-agents` 1.0.7 : `client.startSession()` → `SessionHandle` avec `.stream()`
  (AsyncGenerator de SessionEvent) et `.waitForCompletion({answerSchema})` ;
  `SessionRequest.overrides` permet `{"agent.environments[kind=web].start_url": "…"}` ;
  événements : `policy_event {reasoningContent, content, toolReqs}` (pensées),
  `observation_event {image.source}` (captures, URL plateforme → **proxy authentifié
  obligatoire**, repli `client.sessions.getSessionResource`), `MetricsUpdateEvent`
  (coût/tokens fournis), `LiveViewUrlEvent`, `AgentRunStatusChangeEvent`.
- **Résolution Node** : `node_modules` vit sous `hai-admin-mcp/` → tout module qui importe
  `hai-agents`/`zod` DOIT vivre sous `hai-admin-mcp/` ; `demo/` n'importe que des builtins
  `node:` et des chemins relatifs vers `../hai-admin-mcp/lib/`.
- Filtres Booking par URL **vérifiés en live le 11/09** (paramètre `nflt`, séparés par `;`) :
  `class=3|4|5` (étoiles), `review_score=70|80` (7+/8+), `mealplan=1` (petit-déj),
  `hotelfacility=107` (wifi) / `17` (navette) / `5` (room service) / `8` (réception 24h) /
  `3` (restaurant) / `185` (accessible PMR), `distance=1000|3000|5000`, `fc=2` (annul.
  gratuite), `ht_id=204` (hôtels), `selected_currency=EUR`. Pas de filtre « business
  center » ni « room service 24h » → à vérifier sur la fiche hôtel (étage B).
- Mesures réelles 31/08 : ~0,006 $/step, sessions 4-18 min, concurrence 3 (file au-delà),
  `waitForSeconds` ≤ 25, plafond d'affichage Booking 9 chambres/type, pannes WebDriver
  transitoires possibles (leçon : échec de suivi ≠ échec de session — se rattacher via
  l'id avant de relancer).

## Arbitrages retenus

- **`rebooking.mjs` v1 reste INTACT** (artefact du POC démontré, pas de git → zéro risque
  de régression). La v2 vit dans `hai-admin-mcp/lib/` (code repris par copie) + un CLI
  mince `tools/rebooking-v2.mjs`. Étape 0 recommandée : `git init` + commit initial
  (à proposer à l'utilisateur au moment de l'exécution).
- **Découverte = 1 session, 2 passes** (socle Y puis filtre premium) — dédup native,
  1 seul point de panne au lieu de 3, coût minimal. Classement par tier fait en CODE.
- **Serveur `node:http` natif**, zéro dépendance nouvelle, port 4310, bind 127.0.0.1.
- Schéma relevé enrichi avec enums `non_precise` (véracité : « déclaré par la
  plateforme », conformité PARTIELLE ≠ échec).
- **Allocation incrémentale** : `allocate()` pur, rejoué à chaque relevé terminé → le plan
  se remplit à l'écran pendant la 2e vague (lignes marquées « provisoire » jusqu'au
  dernier relevé).
- **Mode simulation** (« Mode démonstration (sans agents) ») : rejoue des fixtures
  enregistrées + captures PNG locales en ~90 s, zéro token — filet de sécurité du jour J.

## Politique d'hébergement (modèle JSON, défauts)

```
cabins: {
  J: { min_stars: 4, max_stars: 5, required_amenities: ["wifi_free","room_service_24h","workspace"],
       nice_to_have: ["airport_shuttle","restaurant_late"], price_cap_eur: 250,
       allow_above_cap_if_no_alternative: true },
  W: { min_stars: 3, max_stars: 4, required_amenities: ["wifi_free","breakfast_available"],
       nice_to_have: ["airport_shuttle"], price_cap_eur: 130, allow_above_cap_if_no_alternative: true },
  Y: { min_stars: 3, max_stars: null, required_amenities: ["wifi_free"],
       nice_to_have: ["airport_shuttle","breakfast_available"], price_cap_eur: 80,
       allow_above_cap_if_no_alternative: true } },
global: {
  priorities: ["pmr","famille","J","W","Y"],
  rooming: { family_unit_max: {adults:2, children:2}, beyond: "two_rooms_same_hotel",
             infants_no_capacity: true },
  overlays: { pmr: {require_accessible: true, distance_weight_boost: 2.0, allow_tier_upgrade: true},
              famille: {require_family_room_or_two_rooms_same_hotel: true} },
  scoring: { w_review: .35, w_stars_fit: .15, w_distance: .25, w_price_headroom: .25 },
  discovery: { search_radius_km: 5, min_review_score: 7.0, n_socle: 8,
               max_candidates: 10, max_hotels_stage_b: 5 },
  negotiated_rates: false /* verrouillé */, currency: "EUR", free_cancellation_preferred: true }
```

- La **cabine EST le tier** ; Flying Blue ne joue que sur l'ordre intra-tier (Gold+
  servis d'abord). PMR/famille = **overlays** cumulables. `breakfast_available` se calcule
  depuis `rooms[]` (≥1 variante avec petit-déj), pas depuis `amenities`.
- `conformityOf` : filtre dur (étoiles min, required satisfaits — `room_service_24h`
  exige l'enum `"24h"`, `"non_precise"` → PARTIELLE « à confirmer » —, ≥1 chambre sous
  plafond) → CONFORME / PARTIELLE(missing[]) / NON_CONFORME ; `max_stars` dépassé =
  « surclassé », jamais exclu. Score souple = w_review·(note/10) + w_stars_fit·fit +
  w_distance·max(0,1−km/rayon) + w_price_headroom·marge + 0,02/nice_to_have.
- Allocation gloutonne v1 conservée (dédup variantes tarifaires par type physique,
  annulation gratuite prioritaire) + parcours CONFORME→PARTIELLE→HORS_BAREME (si
  dérogation)→ESCALADE DESK. Colonne **`conformite`** dans le plan
  (ex. `PARTIELLE (manque: room_service_24h [non précisé])`).

## Pipeline agents

**Étage A — Découverte (1 session, maxSteps 35, maxTimeS 800, start_url via overrides)** :
recherche de zone « Suvarnabhumi Airport Bangkok » sur Booking, 2 passes par édition
d'URL `nflt` (socle Y : `class=3;class=4;class=5`, wifi, `review_score=70`,
`distance=5000`, `ht_id=204` ; passe premium : `class=4;class=5;hotelfacility=5`),
lecture des CARTES de résultats uniquement (aucune fiche ouverte) → `discoverySchema` :
`candidates[≤10] {name, url, stars, review_score, review_count, price_from_per_night,
distance_km, amenities_seen[], free_cancellation_seen, tier_hints[]}` + `searches_done[]`
+ `notes`. Retry ×1 ; en dernier recours repli UI « liste v1 » (4 hôtels du POC).

**Étage B — Relevés (≤5 sessions = `max_hotels_stage_b`, maxSteps 45, maxTimeS 900,
staggerMs 25 s, concurrence 3)** : session démarrée **directement sur la fiche** (URL
candidate + dates + `selected_currency=EUR` via overrides). Relevé des chambres (comme v1
+ `family_capable`) PUIS, même page, section Équipements → `releveSchema` : niveau hôtel
`{stars, review_score, review_count, distance_to_airport_km, amenities {wifi_free,
room_service: "24h"|"oui"|"non"|"non_precise", workspace, airport_shuttle:
"gratuite"|"payante"|"non"|"non_precise", restaurant_late, accessible}}`. Interdiction de
substituer ; `found=false` → le code prend le candidat suivant du tier (événement
`warning`). `groupId = bkk-v2-{checkin}-{runId}` (runId base36 horodaté, présent dans
tous les événements et noms de fichiers).

**Prompts** : squelettes français détaillés dans les consignes ci-dessus (méthode URL
d'abord, filtres UI en repli ; « déclaré par la plateforme, ne rien déduire,
`non_precise` sinon » ; garde-fous no-booking/CAPTCHA identiques v1).

## Serveur, SSE, UI

Routes (`switch` sur method+pathname, helpers sendJson/readBody, ~10 routes) :
`GET /` + statiques (liste blanche) · `GET /api/config` (défauts + presets + runInProgress)
· `GET|POST /api/presets` · `POST /api/generate-passengers` (stats en retour, copie
`data/passagers-demo.csv`) · `POST /api/passengers` (upload CSV texte, validation
colonnes) · `POST /api/run` {policy, avion, scenario, simulate, hotels?} → 202 {runId} /
**409 si run en cours** · `POST /api/cancel` (handle.cancel() sur les sessions actives)
· `GET /api/events` (SSE) · `GET /api/state` (instantané) · `GET
/api/screenshot?hotel=&seq=` (**proxy authentifié** — paramètres = clés d'état internes,
jamais une URL cliente → SSRF impossible ; fetch bearer ou getSessionResource ;
Cache-Control private) · `GET /api/outputs/:file` (liste blanche, attachment).

Protocole SSE (`id:` monotone, `event:`/`data:` JSON une ligne) — types : `phase`
(preparation→generation→besoins→discovery→releves→allocation→sorties→done),
`agent_status` {hotel, sessionId, status, steps, liveViewUrl, queued}, `agent_thought`
{text ≤400 car., action}, `screenshot` {hotel, seq} (signal seul, image via le proxy,
throttle 1/2 s/agent, dernière toujours émise), `candidate`, `plan_row` {index, total,
row+conformite, provisoire}, `metrics` {totalCostUsd, totalTokens, totalSteps, parAgent}
(agrégat des MetricsUpdateEvent), `warning`, `log`, `done`, `error` {fatal}. Reconnexion :
tampon 1000 événements + `Last-Event-ID`, sinon `snapshot` (état complet re-rendable) ;
le run vit dans le process serveur → onglet fermable pendant les 20-30 min.

UI (vanilla, FR, présentable client) : colonne formulaire repliable — fieldsets
*Politique* (par cabine : étoiles, cases équipements, plafond €/nuit ; chambrage ;
priorités), *Avion* (A350-900, sièges J/W/Y, « Générer la liste » + upload + stats),
*Scénario* (zone fixe BKK, check-in, nuits, seed, case « Mode démonstration ») ; presets ;
bouton « Lancer la prise en charge ». Zone principale : frise de phases, cartes agents
(statut couleur, dernière pensée, vignette capture cliquable, lien « Vue live H »),
bandeau coût/tokens/pas, tableau du plan qui se remplit (escalades surlignées), panneau
final avec téléchargements.

## Coûts & durées attendus (base mesures 31/08)

Découverte 1 session ~6-12 min ~0,21 $ · Relevés 5 sessions (2 vagues de 3) ~10-22 min
~1,35 $ · marge 20 % → **total run réel 18-30 min, <2 €**. Mode simulation : ~90 s, 0 €.
Boutons de réglage : max_hotels_stage_b 5→4, maxSteps B 45→40, n_socle 8→6.

## Risques clés

Candidat découvert puis indisponible → substitution par le code (candidat suivant) ·
anti-bot pages de résultats depuis le runner cloud → repli filtres UI puis
`network.managedProxy`, jamais de contournement CAPTCHA · véracité équipements →
« déclaré par la plateforme », `non_precise` = à confirmer · plafond 9 chambres/type →
borne basse + escalade chiffrée · pannes WebDriver → rattachement par id avant relance,
retry ×1 · clé API jamais côté navigateur (proxy par clés d'état) · un seul run à la fois
(409) · crash serveur → sessions H continuent, `collect-sessions.mjs` reste compatible ·
chemins Windows (`fileURLToPath`, jamais cwd) · CSV Excel = UTF-8 BOM conservé.
